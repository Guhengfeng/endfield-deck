# 工作流方案（Playbook）：不写代码的那一半

这一篇是**方法论层**。前面几篇讲的是"怎么把色算对、怎么把版式排对"，这一篇讲的是**"一个演示稿项目从接到需求到交出成品，中间该做什么决策、产出什么、怎么验收"**。

做 PPT 之前先读这篇定流程，再读 `variants-gallery.md` 选方案。

---

## 一、端到端八阶段

| 阶段 | 做什么 | 产出 | 过关标准 |
|---|---|---|---|
| ① 需求澄清 | 明确受众、时长、场合、主题色倾向、忌讳 | 一份需求清单 | 每个歧义点都有明确答案或明确假设 |
| ② 资料核验 | 真实图片 + 数据出处 | 素材表 + 考据表 | 图片可溯源、数字有出处、不用 AI 生图 |
| ③ 叙事结构 | 定页数与每页承担的信息 | 10 页结构表 | 每页一句话说清"这页为什么存在" |
| ④ 主题选型 | 跑 accent_gen，选强调色与版式方案 | 变体卡 + 方案对比图 | 对比度、语义、面积三闸全过 |
| ⑤ 版式落地 | 写 DSL 源文件 | `slides/*.slide` | lint 零诊断 |
| ⑥ 讲稿撰写 | 逐页口播 + 备注 | notes + 讲稿 docx | 可直接照读，无错漏 |
| ⑦ 验收 | 四步门禁 | 验收报告 | 机器 + 人工双过 |
| ⑧ 交付 | 命名、备份、清理、说明 | 成品清单 | 用户拿到手就能用 |

**不要跳阶段。** 跳过 ① 直接写 DSL，一定会在 ⑦ 返工；跳过 ② 一定会在 ③ 被事实打脸。

---

## 二、需求澄清清单

### 必问的（缺了会返工）

- **受众与场合**：单位内部宣讲？公开报告会？评委席？——决定字号下限和措辞正式度
- **时长**：决定页数与每页字数（经验值：10 页 ≈ 12 分钟）
- **主题色**：给方向（"用红色"）还是给精确值（"#A62B1F"）
- **忌讳**：有没有不能出现的词、不能用的元素
- **是否要讲稿**：要逐页对应稿，还是只要 PPT

### 问法规范（重要）

用户明确要求过：**不要反复催着让用户选，先给对比方案再让用户定。**

所以澄清时不要问"你想用哪种红色？"，要给：

> 三个候选，同一页型同结构，只换强调色：
> A 国旗红 #C8102E（白字压红 5.88:1）
> B 深中国红 #A62B1F（白字压红 7.03:1，块+字都合规）
> C 暗红 #8C1A11（9.25:1，最沉稳）
> 实拍图见 `examples/variants/theme-3red.jpg`。我建议 B，理由是它是唯一能一色两用的。

**同理**：用户说"要红色主题但不要全红"时，答案是三个**版式**方案（左红右浅 / 上红下浅 / 浅底红块）+ 实拍，不是三个孤立的色块。

### 确认要快

用户回复确认时**第一时间执行**，不要为了"更全面"再追加一轮追问。已经确认的方案就照做。

## 三、资料核验方案

### 图片

- **默认用真实网络图片，不用 AI 生成**（除非用户明确要生成图）。
- 图片要落在 `assets/`，且**与 PPTX 同级**（引擎的图片根目录 = PPTX 所在目录）。
- 染色（染红/染蓝）走 `tint_assets.py` 之类的脚本，别手改位图。
- 每张图记一行素材表：来源站点 + 用途 + 对应页码。

### 数据

每一个出现在页面上的数字都要有出处（年份、型号、数量、金额）。做法：

1. 搜集时记下 URL 与原文表述
2. 写进页面前，先做"数据考据表"（页码 / 数字 / 出处 / 原文）
3. 页面上的表述与考据表**逐条对齐**，不加工、不外推

**案例**：本项目里「401」被用户质疑"是什么"——它是"长征一号"核潜艇舷号。**数字出现在页面上就必须能被解释**，否则就是事故。

### 自证性文案的坑

页面上写"全部是真实照片""一张 AI 生成的都没有"这类**元信息/自证**，正式宣讲时上台念会突兀。**默认不写**；用户没要求就不要自证。

## 四、叙事结构方案

### 通用 10 页结构

| 页 | 角色 | 作用 |
|---|---|---|
| 1 | 封面 | 人/事 + 一句话定性 |
| 2 | 导语 | 抛出问题或悬念 |
| 3 | 关键选择 | 三个并置的事实或转折点 |
| 4 | 数据/成绩 | 数字主导的一页 |
| 5 | 困难 | 具体处境（不是空喊） |
| 6 | 高潮 | 名言/画面/情绪高点 |
| 7 | 时间轴 | 年份串叙事 |
| 8 | 代价 | 付出的东西（家庭/健康/时间） |
| 9 | 回响 | 影响与传承 |
| 10 | 收尾 | 落点与一句可带走的话 |

### 人物精神类专用结构（本案例采用）

**生平 → 选择 → 代价 → 回响**四段式，把 10 页分配为：

- p1–2 身份与时代（他是谁、为什么这件事重要）
- p3–4 选择与转折（做了什么选择、代价是什么）
- p5–7 过程与磨砺（具体细节、年份、困境）
- p8–9 代价与回响（牺牲了什么、留下了什么）
- p10 收束与追思

**要点**：精神不是形容词堆出来的，是**从事实里长出来的**。每页至少一件可核验的具体事（一个年份、一个动作、一句原话）。

### 其他题材的换法

- **群像/团队**：按"一个共同命题 + N 个切面"组织，每页一个人，每人一句精神标签
- **产品发布**：痛点 → 方案 → 证据 → 路线图 → 呼吁
- **汇报/年度总结**：结论先行 → 数据 → 归因 → 计划

## 五、文案方案

### 字号阶梯（投影场景）

| 层级 | 字号 | 用途 |
|---|---|---|
| 主标题 | 40px | 每页标题 |
| 副标题 | 28–32px | 引文、金句 |
| 正文 | 20–24px | 主体文字（可照读） |
| 辅助 | 17–19px | 说明、图注 |
| 最小 | **16px** | 页码、来源行、眉标 |

- **层级跳跃 ≥3px**，否则投影上看不出主次。
- 最小字号不低于 16px —— 低于这个值在会议室投影上基本读不了。
- 页眉用**宽体大写英文 + `//` 前缀**，是这套视觉语言的一部分。

### 字数口径

- 统计口径：**汉字**（不计 notes、注释、来源行、页码、装饰文本）。
- 工具：`scripts/count_words.py <slides目录>`。

### 字数与时长的换算

照读语速按 **220–260 字/分钟**（比日常说话慢，含换气停顿）：

| 正文净字 | 净口播时长 | 留白后实际 |
|---|---|---|
| 1200 | 5–6 分钟 | 6–7 分钟 |
| 1800 | 7–8 分钟 | 9–10 分钟 |
| 2200 | 9–10 分钟 | 11–13 分钟 |
| 3000 | 12–14 分钟 | 14–16 分钟 |

本案例最终 **2231 字 ≈ 12 分钟**。

### 各页字数配比（10 页 / 2200 字量级）

| 页型 | 建议字数 |
|---|---|
| 封面 | 80–120 |
| 导语 | 180–240 |
| 要点/列表页 | 300–360 |
| 数据页 | 200–260 |
| 高潮/引言页 | 120–180（留白多） |
| 时间轴 | 260–320 |
| 收尾 | 150–200 |

**高潮页故意少字** —— 念白之外要留画面说话的余地。

## 六、讲稿方案

### 双轨结构

- **PPT 内**：notes 写逐页口播稿（上台照着念的那份）
- **PPT 外**：一份逐页对应的 DOCX（左边缩略图，右边讲稿，便于打印和提前过稿）

### DOCX 的做法

1. 每页 = 一张**终版截图**（不是旧版截图，必须逐张 MD5 校验）+ 对应讲稿
2. 加原生 TOC（目录页）
3. 强调色同步 PPT（讲稿里的重点句用同一 accent 标色）
4. 讲稿字数应 ≥ PPT 正文净字（讲稿会补过渡句、停顿提示）

### 讲稿内容结构（每页）

```
【第 04 页 · 三十年】

  画面说明：左侧深红面板是"30"这个数字，右侧是时间轴…

  口播：
  这里要说一句容易被跳过的背景——…
  （停顿）
  1958 年到 1988 年，整整 30 年…
```

## 七、验收方案（四步门禁）

### 机器门禁

```bash
bash scripts/lint_deck.sh deck.pptx slides/                                  # ① lint 零诊断
python scripts/build_deck.py --slides slides/ --out deck.pptx --accent "#…"   # 构建时自带文本校验
python scripts/scan_overflow.py --pptx deck.pptx --shots shots/ --accent "#…" # ② 几何 + 像素
python scripts/count_words.py slides/                                        # ③ 字数与时长
```

### 人工复检清单（机器抓不到的部分）

- [ ] 逐页看截图：有没有文字被切、压行、重叠
- [ ] 强调色面积是否在闸内（`scan_overflow` 会报数字）
- [ ] 深色页上的文字是否全部为白/浅色（不是 accent）
- [ ] 强调色是不是**全片只有一种**
- [ ] 备注是否每页都有
- [ ] 图片引用是否 0 断链
- [ ] 成品能否被 `python-pptx` 正常打开、页数正确

### 交付前最后一道

把成品**从头翻一遍**（像观众一样从头看到尾），不要只看自己改过的页。**改过的页最容易有残留。**

## 八、交付与回滚方案

### 命名

```
<主题>-照读PPT-<配色>终稿.pptx          # 主成品
<主题>精神分享-逐页演讲稿-<配色>.docx     # 讲稿
```

### 成品清单（交付时一并报给用户）

| 文件 | 说明 |
|---|---|
| `xxx-终稿.pptx` | 主交付 |
| `xxx-逐页演讲稿.docx` | 讲稿 |
| `xxx-DESIGN.md` | 变体卡、豁免说明、数据考据、踩坑记录、验收记录 |
| `examples/…/shots/` | 终版截图（讲稿缩略图来源） |

### 回滚

- **每次大改前先备份**：`slides/` 源文件 + 上一版 pptx 一起进 `_vN_backup/`
- 源文件是唯一真相源 —— **改内容只改 `slides/*.slide`，不要改 pptx**
- 覆盖 pptx 报 PermissionError（Windows 文件锁，多半被预览进程占用）→ **换新文件名**，不要硬删

### 清理

- 根目录只留成品 + 备份；实验产物归 `_variants/`
- 删除前先确认文件锁（`Permission denied` = 被预览进程占用）

## 九、返工方案（用户说 X 时怎么办）

| 用户说 | 真实诉求 | 动作 |
|---|---|---|
| "太丑了，重新生成" | 不是局部美化问题，是整体版式不成立 | 回到 `variants-gallery.md` 换**方案**，不是微调参数 |
| "字太小 / 看不清" | 投影可读性 | 字号阶梯整体上抬 + 检查层级跳跃 ≥3px + 精简文案换行 |
| "字太少" | 内容不足 | 补**事实**（数据/细节/原话），不是形容词 |
| "要红色主题" | 换色 | 跑 accent_gen → 换 accent → 重建 → 重新验收 |
| "第 X 页不要全红" | 强调色铺太多 | 换 L 类版式（左红右浅），重新算面积 |
| "这里前后都没显示完整" | 文本被裁 | 查行高/容器高度/字号，`scan_overflow` 报坐标 |
| "这句多余 / 别强调有没有 AI" | 内容取舍 | 直接删，别用"保留但弱化"糊弄 |
| "再给我几个方案对比" | 需要决策依据 | 渲染实拍图 + 实测数据，然后给推荐并说明理由 |

### 迭代加速

全量重建 10 页很慢。排查单页问题时：

1. 只写该页 DSL → 只 upsert 该页 → 只截该页
2. **必须做像素差分**（对比新旧截图），否则"改了没生效"会被误当成"改了没用"
3. upsert 静默失败时（命令返回 0 但页面没变），用 `slidep inspect` 比对文本

## 十、协作规范

- **先解释，再动手**：动手前把"为什么这么做、要做什么"讲清楚
- **给对比，不给选项**：至少 3 个候选 + 实拍 + 实测数据 + 我的推荐和理由
- **确认后第一时间执行**，不追加第二轮追问
- **如实报告**：产物有问题就直说，包括"我此前说错了"（例如把"源文件里的黄色 token"误判成"成品双色混用"）
- **交付即给成品路径**，不只说"做好了"
